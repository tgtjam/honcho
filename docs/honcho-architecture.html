01 Visión General

Honcho es infraestructura de memoria para agentes de IA. Almacena conversaciones y eventos, razona en segundo plano para extraer conclusiones sobre los participantes, y expone esas conclusiones a través de una API de chat, búsqueda semántica y representaciones estáticas.

🧠 Reasoning-first

Extrae conclusiones de conversaciones usando LLMs — no solo matching de chunks.

👥 Peer-centric

Usuarios, agentes y grupos son "peers" — entidades de primera clase que evolucionan.

🔌 Multi-SDK

SDK para Python, TypeScript, MCP, Hermes, Claude Code.

🏠 Self-hosted

Open source (AGPL-3.0), corre con Docker + pgvector + Redis.

02 Arquitectura

Honcho se divide en tres planos: Storage (síncrono), Insights (asíncrono), y Embeddings (local).

Componentes

API (FastAPI)

Puerta de entrada REST. CRUD de workspaces, peers, sessions, messages. Endpoint de chat y búsqueda.

Database (pgvector)

PostgreSQL 15 con extensión pgvector. Almacena peers, sesiones, mensajes y vectores de embedding (768d).

Redis

Cola de trabajos para el deriver + caché de representaciones.

Deriver

Worker asíncrono que consume la cola de Redis, genera representaciones, resúmenes y observaciones.

Ollama

Servidor local de embeddings via nomic-embed-text-v2-moe (768d). API compatible con OpenAI.

Dreamer

Sistema de razonamiento profundo: descubre patrones que el deriver no detecta. Opera en segundo plano con árboles de similitud.

03 Honcho Loop

El ciclo fundamental de Honcho: Store → Reason → Query → Inject. Cada mensaje que entra desencadena procesamiento asíncrono.

Flujo detallado

PasoQué ocurreComponente
1. StorePeers envían mensajes a una sesión via API REST. Se persisten en pgvector y se encolan en Redis.API pgvector Redis
2. ReasonDeriver consume la cola: actualiza representaciones del peer, genera observaciones, crea resúmenes de sesión.Deriver LLM
3. QueryEl cliente pregunta via chat, búsqueda semántica, o contexto de sesión. Honcho sintetiza usando representaciones + conclusiones.API pgvector
4. InjectEl resultado se inyecta al prompt del agente (Hermes, Claude Code, etc.) como contexto enriquecido.Agente

Primitivas

PrimitivaDescripción
WorkspaceContenedor raíz. Aísla datos por caso de uso.
PeerParticipante — humano o agente de IA.
SessionContexto conversacional. Muchos-a-muchos con peers.
MessageUnidad atómica de datos (comunicación peer-to-peer o chunk de documento).
ConclusionInferencia extraída por el deriver sobre un peer.
RepresentationSnapshot estático de lo que Honcho sabe de un peer.
Peer CardResumen compacto de identidad del peer.

04 Deriver Pipeline

El deriver es el corazón del procesamiento asíncrono. Corre en un contenedor separado y consume mensajes desde la cola de Redis.

Tipos de trabajo

TipoQué haceModelo
representationActualiza la representación del peer: extrae conclusiones deductivas e inductivas de los mensajes recientesDeepSeek v4 Flash
summaryGenera o actualiza el resumen de una sesión cuando se acerca al límite de tokensDeepSeek v4 Pro
dreamProcesamiento nocturno (o periódico) para encontrar patrones profundos que el deriver diario no captaDeepSeek v4 Pro

Observaciones y conclusiones

El deriver genera observaciones que se almacenan en colecciones vectoriales internas, keyed por par (observer, observed). Esto permite tanto auto-representación (observer == observed) como modelado cross-peer (qué sabe el peer A sobre el peer B).

Deduplicación

Configurado con WORKING_REPRESENTATION_DEDUP_DISTANCE=0.35 — observaciones semánticamente similares se fusionan para evitar redundancia en la representación.

05 Dreamer — Razonamiento Profundo

El Dreamer es un sistema de razonamiento asíncrono que opera en ciclos programados (no en tiempo real como el deriver). Descubre patrones latentes y conexiones que el deriver no detecta en el procesamiento diario.

🧬 Especialistas

Múltiples "especialistas" con prompts distintos analizan al peer desde diferentes ángulos (personalidad, metas, frustraciones, etc.)

🌲 Árboles de similitud

Usa CoverTree, RP-Tree, LSH y otros algoritmos para encontrar clusters de observaciones relacionadas.

🔄 Surprisal

Detecta observaciones "sorprendentes" — aquellas que contradicen la representación actual del peer, gatillando revisión.

06 Configuración TGT One

Nuestra configuración local usa DeepSeek API como LLM principal y Ollama local para embeddings (nomic-embed-text-v2-moe, 768d).

Variables de Entorno Esenciales

# LLM Principal (DeepSeek)
LLM_OPENAI_API_KEY=sk-...deepseek...

# Embeddings via Ollama local (768d)
EMBED_MESSAGES=true
EMBEDDING_VECTOR_DIMENSIONS=768
EMBEDDING_MODEL_CONFIG__TRANSPORT=openai
EMBEDDING_MODEL_CONFIG__MODEL=nomic-embed-text-v2-moe
EMBEDDING_MODEL_CONFIG__OVERRIDES__BASE_URL=http://ollama:11434/v1

# Vector store
VECTOR_STORE_TYPE=pgvector

# Deriver
DERIVER_MODEL_CONFIG__TRANSPORT=openai
DERIVER_MODEL_CONFIG__MODEL=deepseek-v4-flash
DERIVER_MODEL_CONFIG__OVERRIDES__BASE_URL=https://api.deepseek.com/v1
DERIVER__WORKING_REPRESENTATION_DEDUP_DISTANCE=0.35
DERIVER__FLUSH_ENABLED=true

08 API Reference

Todas las rutas siguen el patrón /v3/{resource}/{id}/{action}. Los endpoints de listado/búsqueda usan POST para aceptar bodies de filtro.

Routers principales

RecursoEndpoint baseOperaciones clave
Workspaces/v3/workspacesCRUD + search
Peers/v3/workspaces/{id}/peersCRUD + chat (dialectic) + messages + representation
Sessions/v3/workspaces/{id}/sessionsCRUD + clone + manage peers + get context
Messages/v3/workspaces/{id}/sessions/{sid}/messagesCreate (batch hasta 100), upload file, list, get, update
Conclusions/v3/workspaces/{id}/conclusionsCRUD + semantic search + delete
Keys/v3/workspaces/{id}/keysCreate scoped JWTs
Webhooks/v3/workspaces/{id}/webhooksRegister endpoint, list, delete, test

Chat Endpoint (Dialectic)

El endpoint POST /v3/workspaces/{wid}/peers/{pid}/chat es la interfaz principal de consulta. Acepta preguntas en lenguaje natural sobre un peer y usa reasoning multi-nivel para responder.

# Consultar sobre un peer
curl -X POST http://localhost:8000/v3/workspaces/my-app/peers/alice/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "¿Qué estilo de aprendizaje prefiere alice?", "reasoning_level": "low"}'

09 Comandos Útiles

Gestión del stack

$ docker compose up -d # Levantar todo
$ docker compose down # Detener todo
$ docker compose logs -f api # Logs API en vivo
$ docker compose logs --tail=30 deriver # Últimos logs del deriver
$ docker compose up -d --build api # Reconstruir API
$ docker compose up -d --build deriver # Reconstruir deriver
$ docker compose ps # Estado de servicios

Healthcheck

$ curl http://localhost:8000/health # → {"status":"ok"}

Embeddings — configuración

# Si se cambia el modelo de embeddings, hay que re-indexar
$ docker compose run --rm --entrypoint python api scripts/configure_embeddings.py\n\   --yes --batch-size 50

Scripts útiles

# Forzar regeneración de todos los embeddings
$ docker compose run --rm --entrypoint python api \
  scripts/generate_message_embeddings.py

# Ver estado de la cola
$ docker compose exec redis redis-cli LLEN "honcho:queue:default"

# Ver representaciones de todos los peers
$ docker compose exec database psql -U postgres -c \
  "SELECT * FROM working_representations;"

Backup y restore

# Backup de la base de datos vectorial
$ docker compose exec -T database pg_dump -U postgres > ~/backups/honcho/honcho-$(date +%F).sql

# Restore
$ cat honcho-2025-06-10.sql | docker compose exec -T database psql -U postgres

SDK Python — test rápido

$ pip install honcho-ai

>>> from honcho import Honcho
>>> h = Honcho(workspace_id="test", base_url="http://localhost:8000")
>>> alice = h.peer("alice")
>>> ses = h.session("s1")
>>> ses.add_messages([alice.message("hola, me llamo alice")])
>>> alice.chat("¿cómo se llama este peer?")
