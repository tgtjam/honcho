01 Escenarios de Desastre

Tres niveles de desastre, ordenados por severidad:

Nivel 1 — Bajo

Qué pasa: Docker compose detenido, contenedores rotos, config corrompida.

Daño: Los volúmenes Docker sobreviven. BD y datos intactos.

Recuperación: docker compose up -d --build

Nivel 2 — Alto

Qué pasa: Volúmenes Docker perdidos (reset WSL de Docker, disco corrupto).

Daño: BD PostgreSQL perdida. Código en Git intacto.

Recuperación: Instalar desde cero + restaurar backup SQL

Nivel 3 — Crítico

Qué pasa: Máquina completa perdida (WSL reseteado, disco formateado, laptop robada).

Daño: BD + config + código local perdidos. Solo sobrevive GitHub + OneDrive.

Recuperación: Clonar repos + restaurar backup desde OneDrive

04 Instalación Desde Cero

Procedimiento completo si pierde todo (WSL reseteado, clon fresco).

1️⃣ Clonar el repo de setup

$ git clone https://github.com/tgtjam/honcho-tgtjam-setup.git $ cd honcho-tgtjam-setup

2️⃣ Configurar .env

$ cp .env.example .env $ nano .env # pegar LLM_OPENAI_API_KEY real

Si el backup está en OneDrive, copiar el .env directamente:

$ cp /mnt/c/Users/JAM/OneDrive/Documentos/Hermes-Bacups/config/env_20260611_033622 .env

3️⃣ Clonar Honcho upstream + aplicar nuestra config

$ cd .. $ git clone https://github.com/tgtjam/honcho.git $ cd honcho $ cp ../honcho-tgtjam-setup/docker-compose.yml . $ cp ../honcho-tgtjam-setup/config.toml . $ cp ../honcho-tgtjam-setup/.env.example . $ # copiar el .env real desde el paso 2

4️⃣ Descargar modelo de embeddings

$ docker compose up -d ollama $ docker exec honcho-ollama-1 ollama pull nomic-embed-text-v2-moe

5️⃣ Construir y levantar todo

$ docker compose up -d --build

6️⃣ Si hay mismatch de dimensiones de embedding

$ docker compose stop api $ docker compose run --rm --entrypoint python api \ scripts/configure_embeddings.py --yes $ docker compose up -d api

7️⃣ Restaurar backup SQL (si existe)

Si estás recuperando de un desastre Nivel 2+, NO uses la BD vacía. Ve a la sección de restore.

8️⃣ Verificar

$ curl http://localhost:8000/health {"status":"ok"} $ docker compose ps # todos healthy/up

05 Restaurar BD PostgreSQL

Para desastres Nivel 2 (volúmenes Docker perdidos).

⚠️ Precaución

La BD debe estar vacía antes de restaurar. Si hay datos existentes, el pg_restore fallará con duplicados.

1️⃣️ Asegurar que el contenedor database esté corriendo

$ docker compose up -d database $ sleep 5

2️⃣️ Elegir el backup más reciente

$ ls -1t ~/backups/honcho/db/*.sql.gz | head -1 # o desde OneDrive: $ ls -1t /mnt/c/Users/JAM/OneDrive/Documentos/Hermes-Bacups/db/*.sql.gz | head -1

3️⃣️ Restaurar

$ gunzip -c ~/backups/honcho/db/honcho_20260611_033622.sql.gz \ | docker exec -i honcho-database-1 psql -U postgres -d postgres

4️⃣️ Verificar dimensiones de embedding

Si la BD tenía vectores con dimensiones distintas a 768 (el modelo actual), el API no arranca:

StartupValidationError: public.documents.embedding dim (X) does not match EMBEDDING_VECTOR_DIMENSIONS (Y)

Solución:

$ docker compose stop api $ docker compose run --rm --entrypoint python api \ scripts/configure_embeddings.py --yes $ docker compose up -d api

5️⃣️ Verificar

$ curl http://localhost:8000/health # {"status":"ok"}
↑ volver

06 Restaurar Hermes (state.db)

Para desastres Nivel 3 (WSL reseteado).

⚠️ Nota importante

Los archivos SQLite de Hermes están en el filesystem de WSL (/home/jam/.hermes/), NO dentro de Docker. Sobreviven a un reseteo del backend de Docker, pero se pierden si se resetea WSL completo.

1️⃣️ Copiar desde OneDrive

$ cp /mnt/c/Users/JAM/OneDrive/Documentos/Hermes-Bacups/sqlite/state_20260611_033622.db \ ~/.hermes/state.db $ cp /mnt/c/Users/JAM/OneDrive/Documentos/Hermes-Bacups/sqlite/kanban_20260611_033622.db \ ~/.hermes/kanban.db

2️⃣️ Restaurar perfiles

# Cada perfil tiene su propio state.db $ for f in /mnt/c/Users/JAM/OneDrive/Documentos/Hermes-Bacups/sqlite/*_state_*.db; do prof=$(basename "$f" | sed 's/_state_.*//') mkdir -p ~/.hermes/profiles/"$prof" cp "$f" ~/.hermes/profiles/"$prof"/state.db done

3️⃣️ Restaurar script de backup

$ mkdir -p ~/.hermes/scripts $ cp /mnt/c/Users/JAM/OneDrive/Documentos/Hermes-Bacups/config/backup-honcho_20260611_033622.sh \ ~/.hermes/scripts/backup-honcho.sh $ chmod +x ~/.hermes/scripts/backup-honcho.sh
↑ volver

07 Restaurar Script de Backup

Si pierdes solo el script ~/.hermes/scripts/backup-honcho.sh pero el backup en OneDrive está intacto:

📄 Desde OneDrive

Copia el archivo config/backup-honcho_*.sh más reciente a ~/.hermes/scripts/

$ cp /mnt/c/.../config/backup-honcho_*.sh ~/.hermes/scripts/backup-honcho.sh $ chmod +x ~/.hermes/scripts/backup-honcho.sh

🐙 Desde GitHub

El script NO está en ningún repo de GitHub. Solo está en el filesystem local (~/.hermes/scripts/) y en los backups de OneDrive.

🔄 Recrear

Si no hay backup (desastre total), Hermes puede regenerar el script desde la documentación HTML.

Recrear el cron job de Hermes

$ hermes cronjob create \ --name "honcho-backup-daily" \ --schedule "0 4 * * *" \ --script backup-honcho.sh \ --no-agent \ --deliver local

09 Troubleshooting

🛑 El API no arranca

$ docker compose logs api # ver el error exacto
SíntomaCausaSolución
StartupValidationError: embedding dim mismatchLa BD tiene dimensión de vectores distinta a 768configure_embeddings.py --yes
could not connect to serverDB no respondedocker compose logs database
401 UnauthorizedAPI key inválida/expiradaRevisar LLM_OPENAI_API_KEY en .env
Container exits immediatelyError en entrypoint o migracióndocker compose logs api para diagnóstico

🛑 La BD se perdió

Los volúmenes Docker (honcho_pgdata, honcho_redis-data) persisten entre reinicios del contenedor pero no sobreviven a un reseteo del backend de WSL.

Solución: restaurar desde backup SQL (sección #restore-db).

🛑 Honcho no inyecta contexto (memory no funciona)

VerificaciónComando
Estado serviciosdocker compose ps → api debe estar healthy
Healthcheckcurl localhost:8000/health → {"status":"ok"}
API keygrep LLM_OPENAI_API_KEY ~/develop/honcho/.env
Hermes confighermes config get honcho.enabled → debe ser true
Deriver activodocker compose logs --tail=10 deriver → debe mostrar procesamiento

🛑 El backup no se ejecuta

$ hermes cronjob list # verificar que el cron existe $ bash ~/.hermes/scripts/backup-honcho.sh # ejecución manual

🔄 Forzar el cron para que corra ahora

$ hermes cronjob run --job-id 59f646c7800c
